02 · System architecture

A request becomes a durable background job.

Separate services handle the interface, validation, scheduling, computation, storage and monitoring.

The API and workers share PostgreSQL job state and private MinIO storage. The UI polls job status, then requests a signed result URL.

Temporary failures

Default three total attempts with exponential retry delays. The Python processing timeout defaults to 60 seconds.

Worker interruption

Expired reservations allow stalled work to be redelivered. Delivery is at least once; duplicate work is handled.

Private results

Unsigned objects are inaccessible. Signed download links expire after five minutes; default file retention is seven days.

06 · Understanding the dashboard

Batch size, worker count and queue depth differ.

These values describe separate parts of the system, so they do not need to match.

8

Images per batch

A fixed UI and API limit bounds a single request and its memory use. Submit another batch for more images; it is not a total project limit.

1

Connected worker

The default is one BullMQ consumer with concurrency one. Kubernetes can scale worker pods from one to four when waiting work builds up.

0

Queued work

No waiting/delayed jobs at that moment. Check active work separately. When active is also zero, the workers are usually idle.

File and pixel safeguards

Default 10 MB per image and 25 million decoded pixels. Compressed file size alone does not describe processing memory.

Different kinds of parallelism

Batch size counts images submitted together. Concurrency counts jobs per worker. Replicas count worker pods.

Reading metrics correctly

Queue depth = waiting + delayed; active is separate. Progress values are lifecycle milestones, not continuous pixel-level percentages.

CLOUDFRAME · MONITORINGWorker count reports connected consumers; it is not a CPU utilization measurement.07 / 10

09 · Outcome and boundaries

A functioning local demonstration of cloud patterns.

CloudFrame connects a usable image editor to durable asynchronous jobs, private storage, failure recovery and observed Kubernetes worker scaling.

Implemented and demonstrated

Six-page responsive application and real image transformations.Container processing, persistent history, private previews and downloads.Actual recovery tests, observability and KEDA scaling from one to four workers.

Current limitations and next steps

Local single-tenant academic deployment; public cloud hosting is not demonstrated.Add authentication, ownership checks, TLS, secret management, HA and backups for public use.Cancellation is unsupported (409). Optional Ingress and ELK were not deployed/exercised.
Presentation takeaway: the queue decouples requests from compute; Kubernetes and KEDA adjust the number of processing workers.
